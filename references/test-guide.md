# 測試指引（第六種用途）

Phase 0 選了「測試指引」才做。目的：交給**要動手測系統的人**（客戶端的店長、客服、內部 QA、驗收人員）一份 A4 文件，
拿到就知道：

- 用**哪個身分**、哪個帳號代碼登入
- 照**什麼步驟**做（畫面上的字一字不差）
- 每一步**應該看到什麼畫面**（預期畫面＋關鍵截圖）
- 怎麼**打勾**、怎麼判 P／M／F／B／N
- 不對的時候**怎麼回報**（回報到哪、給誰、什麼時候前、一則要寫什麼）

和其他用途的差別：

| | 測試指引 | 整合測試 | 操作說明 |
|---|---|---|---|
| 誰做測試 | **讀者自己**照著做 | 我們（`itest.mjs`）已經跑完 | 不測 |
| 產出 | A4 直式、可列印、可填寫 | 16:9 結果報告 | 16:9 教學 |
| 內容 | 身分、流程步驟＋預期畫面、檢查清單、回報方式 | 通過／未通過／疑慮與截圖 | 怎麼用、設定改了會怎樣 |

A4 是獨立一份 PDF，**不和 16:9 簡報合成**（`Deck(purposes=[…"測試指引"])` 會報錯）。檔名照規則：
`AI GO 租戶名 App名 測試指引 YYYYMMDD.pdf`。參考範例：Bauerfeind 智能客服中心「AI 自動回覆測試指引」（2026-10-16）。

## 流程

```
TG0 範圍 → TG1 盤點身分與流程 → TG2 大綱 ══GH1 使用者核准══ → TG3 截預期畫面 ══G2 截圖驗收══
→ TG4 親自照指引走一遍 ══GH2 預期畫面都對══ → TG5 寫內容＋輸出 ══G4 逐頁目視══ → TG6 交付
```

**關卡不能跳**：GH1 沒核准不截圖；GH2 沒有每一步都實際走過，不寫進預期畫面；G4 沒看過每頁不交付。

### TG0 範圍（先問，`prompts.md` §13）

1. **讀者**：誰拿這份去測（客戶的店長／客服／外部 QA）？用詞深淺跟著讀者
2. **測試站**：測哪個站（demo 租戶、預覽頁、正式站）。給客戶測的通常是 demo 或預覽頁；正式站要使用者明確同意
3. **身分與帳號**：要測哪幾種身分（app 角色白名單）；每個身分的**測試帳號由誰準備、怎麼私下給**——密碼不進文件
4. **範圍**：哪幾條工作流程？有沒有規格或驗收條件可以對？哪些不測（例：真的扣款、推播給客人）
5. **不能做的事**：會對外送出、刪資料、影響正式客人的操作——寫進 `prepare(dont=[…])`
6. **回報方式**：回報到哪裡（LINE 群組／Email／表單）、誰收、期限；有沒有承諾的回覆時效（沒有就不寫 `sla`）

### TG1 盤點身分與流程

- **身分**：讀 app 的角色設定（`aigo-builder` 的使用者授權架構：角色、app 角色白名單）與前端的權限判斷（按鈕／選單／路由的條件）。
  每個身分列「平常做什麼、這次測試重點」；不同身分**看得到／做得到的差異**整理成權限檢查表
- **流程**：從 `present.config.json` 的 `routes`、`discover.mjs` 的 `ui.json`、程式碼找核心工作流程。
  預設比重同操作說明：**核心工作流程 ＞ 可控制的參數 ＞ 其他頁面**。一條流程＝一個讀者會完整做完的事（建立訂單、退款審核、出貨）
- 每條流程記下：用哪個身分、前置條件（要先有什麼資料、要先做完哪條）、步驟（點哪裡、輸入什麼）、每一步做完畫面會怎樣
- 整合測試做過的話，`itest.plan.mjs` 的端到端案例就是很好的流程來源（步驟與預期已經驗證過）

### TG2 大綱（GH1 使用者核准）

照 `templates/guide.outline.example.md` 提給使用者：讀者、測試站、身分表、流程清單（編號、名稱、身分、步數、要不要截圖）、
權限檢查表、不能做的事、回報方式。使用者核准才往下。

### TG3 截預期畫面

- 用 `shoot.mjs` 照截圖計畫拍（`references/screenshot-guide.md`）。**每條流程最多 2 張**，通常是結果畫面
  （列表多了一筆、狀態變了、跳出的提示）；過程中的畫面用文字寫在「預期畫面」欄
- 不同身分的畫面要用該身分的測試帳號拍（另一份 `present.config.json`／`env_file`），不要用管理員帳號假裝
- 截圖的副作用照常還原（`prep_state.py`）；測試資料用前綴（例：`TEST-`）

### TG4 親自照指引走一遍（GH2）

**預期畫面是這份文件的核心，寫錯了測試人員就會誤判。**交付前用每個身分的測試帳號、照文件上的字一步一步走一次：

- [ ] 每一步的操作字樣和畫面一字不差（按鈕名、欄位名、分頁名）
- [ ] 每一步的預期畫面真的會出現（提示文字、列表變化、狀態名稱）
- [ ] 前置條件說得清楚，照著準備就能開始
- [ ] 權限檢查表每一格都實際登入確認過
- [ ] 不能做的事都列了；照步驟做不會碰到正式資料或對外送出

走的過程發現 bug：照核心原則 6 處理（確認是 bug 就修好上線、更新截圖與預期畫面）。修不了的，**不要把錯的行為寫成預期**——
那一條先拿掉或在 `pre` 註明，交付時告訴使用者。

### TG5 寫內容＋輸出

```bash
cp <skill>/templates/guide_content.example.py guide_content.py    # 改 SKILL 路徑，照核准的大綱寫
python guide_content.py                                            # →「AI GO 租戶名 App名 測試指引 YYYYMMDD.html」
node <skill>/scripts/render.mjs --html "AI GO … 測試指引 ….html" --png preview   # 同名 A4 PDF；預覽 2 倍解析度
python <skill>/scripts/contact_sheet.py "preview/p*.png" --cols 4 --rows 2 --cell 560x792 --out disc/pv --no-label   # G4
```

### TG6 交付

- 交 PDF（< 20 MB）；在對話裡列：身分數、流程數、總步數、回報到哪、期限、哪些沒放進來與原因
- 提醒使用者：帳號密碼要另外私下給測試人員
- 測試人員回報回來的問題：確認、修好、在回報單「修正後重測」打勾；需要時改版重出（版本寫在 `version`）

## 頁序與 API（`scripts/guide_kit.py`）

頁序固定，寫的順序不影響（流程之間照呼叫順序，編號 T01、T02…）：

| 頁 | API | 必填 | 內容 |
|---|---|---|---|
| 封面（深底） | `g.cover(sub, goals, meta)` | 自動 | App 名＋測試指引、一句話、三個目標、製作日章、租戶／App／版本／測試站／對象／範圍（N 種身分・M 條流程） |
| 目錄 | `g.toc()` | 自動 | 單欄、依「開始之前／測試流程／判定與回報／可列印表單」分組，頁碼可點；列多自動續頁 |
| 測試準備 | `g.prepare(env, todo, dont)` | 建議 | 環境表（測試站自動第一列）、開始前打勾清單、不要做的事（深底注意框） |
| 身分與帳號 | `g.roles([(身分, 帳號代碼, 平常做什麼, 測試重點)])` | **必填** | 身分表＋「帳號密碼另外私下提供」 |
| 怎麼執行 | `g.howto()` | 自動 | 通用五步＋預期畫面怎麼對 |
| 自訂頁 | `g.slide(part, title, lede, body)` | 選配 | 測試範圍、名詞解釋；排在流程之前 |
| **測試流程** | `g.flow(title, role, goal, steps, pre, shot, caption, passes, fails, minutes)` | **至少一條** | 一條一頁：身分／帳號代碼／前置條件／預估時間 → 步驟表「# ｜操作｜預期畫面｜✓」→ 預期畫面截圖（≤ 2）→ 通過／不通過判準 → 整條結果列（P M F B N、測試者、日期、回報單） |
| 權限檢查 | `g.permissions([(功能, 身分1 預期, …)])` | 選配 | 功能 × 身分矩陣，每格一個勾選框；可以＝綠、看不到／不行＝紅 |
| 判定標準 | `g.judge(critical)` | 自動 | P 通過／M 需改善／F 不通過／B 卡住／N 不適用、嚴重度高中低、重大問題（發現就回報） |
| 回報方式 | `g.report(channel, to, deadline, sla, fields, example)` | **必填** | 回報到／給誰／期限、一則回報要包含（8 項）、回覆時效（有寫 `sla` 才放）、範例訊息（自動用第一條流程產填空範例） |
| 總檢查清單 | 自動 | — | 每條流程一列（＋權限檢查每個身分一列）、P M F B N 勾選、回報單編號；最後一頁有合計與通過率算法；每頁 22 列 |
| 問題回報單 | 自動 | — | 一個問題一張、可複印：編號／流程步驟／身分、嚴重度、做了什麼、預期、實際、截圖、時間裝置、重測結果 |
| 送出前確認（深底封底） | `g.back_cover(checks, contact)` | 自動 | 交出前的打勾清單＋聯絡列 |

`write()` 會擋：缺身分、缺流程、缺回報方式；流程用了沒列的身分；權限表欄數不對；步驟沒寫預期畫面；
流程名超過 20 字、超過 12 步；文件裡出現「密碼：…」「token=…」這類密鑰。

## 判定與統計（印在文件裡，測試人員照這個判）

| 結果 | 什麼時候用 |
|---|---|
| **P 通過** | 每一步都和預期畫面相同，流程完成 |
| **M 需改善** | 流程完成，但文字、版面、速度或提示不理想 |
| **F 不通過** | 做不下去、結果錯誤、看到不該看到的資料，或畫面和預期不同 |
| **B 卡住** | 帳號、資料或環境不對，無法判斷；補齊後再測 |
| **N 不適用** | 這次範圍不含，或這個身分本來就不用做；寫原因 |

整條流程取最嚴重的一步；通過率＝P ÷（P＋M＋F），B、N、未測不算分母。同一條流程重測另填一列，不覆蓋第一次。
