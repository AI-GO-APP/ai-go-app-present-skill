# 寫作指引

## 讀者與語氣

- 讀者是**接手後台的人**，不是工程師。用畫面上看得到的字（按鈕、分頁、欄位名）加「」引用，**一字不差**。
- 繁體中文、台灣用語；句子短；一個項目只講一件事。
- 不寫程式識別字（變數、表名、action 名）。例外：使用者必須親手輸入的值（例：金鑰名稱 `OPENROUTER_API_KEY`）。
- 專有名詞第一次出現就用一句話解釋（例：「Jev 是專門做判定的小模型，不寫文字」）。
- 不寫「強大」「智慧」「無縫」這類形容詞；寫它做什麼、會怎樣。

## 只寫功能與操作，不插播

手冊只回答五件事：**是什麼、在哪、怎麼操作、改了會怎樣、要注意什麼**。其他一律不寫。

探勘時讀過的原始碼、CHANGELOG、評估紀錄會留在腦中，寫的時候很容易滲進去。下面這些**禁寫**：

- **開發歷史與版本演進**：「這個功能在 v12 加入」「原本是…後來改成…」
- **設計理由**：「之所以這樣設計是因為…」「為了避免…所以…」——讀者只需要知道會發生什麼
- **技術架構**：前後端分工、API、模型名稱、資料表、shadow DOM、action 名。例外：使用者必須親手輸入或選擇的值
- **與其他系統的比較**、評價與推銷語（「比傳統客服更…」「大幅提升…」）
- **查證依據**：程式碼位置、「依後端邏輯…」——依據留在工作筆記與 G3 紀錄，不進手冊
- **製作過程**：截圖時修了什麼 bug、哪些畫面拍不到的原因——修了什麼在交付對話裡說（`workflow.md` P7）

**例外：測試報告**（Phase 0 選了才有，見下方「測試報告」）可以寫測試結果。範圍很窄：
只寫指標、定義、結果、樣本、日期、測試範圍與限制；怎麼調出這個數字、與其他系統比較、「大幅提升」
這類評價、版本間的演進仍然禁寫。這些數字只出現在測試報告，其他頁不引用。

**功能展示**（Phase 0 選了才有，見下方「功能展示」）不教操作，但同樣不插播：不寫開發歷史、技術架構、推銷語。

**整合測試**（Phase 0 選了才有，見下方「整合測試」）是測試結果，可以寫問題與技術證據（API 狀態碼、錯誤訊息原文），
但只放在問題頁的偵測紀錄；判讀仍用白話。

介紹只有兩個地方：封面的一句話、目錄頁（目錄與讀法）。分隔頁的「這部分教什麼」也是一句話，講讀完會做什麼，不講背景。

**刪除測試**：這句刪掉，讀者會少做對一件事嗎？不會就刪。

## 內容比重（預設）

1. **核心工作流程**（例：訊息中心）：怎麼找、怎麼切換、一個完整流程從頭到尾、怎麼讀系統給的資訊
2. **可控制的參數與提示詞**：每一個參數「在哪、目前值、改了在什麼情境會有什麼結果」
3. **其他頁面**：一頁一個，講用途與和核心流程的關係
4. **維護**：每天／每週／事件觸發的檢查清單＋目前設定值附錄

## 頁型（templates/deck_content.example.py 各示範一次）

| 頁型 | 什麼時候用 | 組成 |
|---|---|---|
| 封面 | 第一頁 | `d.cover()`：AI GO 圖標、App 名＋手冊名、一句話、**製作日章**、租戶／App／版本／對象、瀏覽器框主畫面 |
| **目錄**（必備） | 第二頁 | `d.toc()` 或省略（自動）：每個 PART 一欄、每頁一列＋可點頁碼；底部讀法（編號、情境→結果、注意）。頁標題就是目錄列，寫短 |
| 地圖 | 第三頁 | 左：所有頁面一句話；右：一筆資料在系統裡的旅程（方塊＋箭頭） |
| **功能展示**（選了才有） | 目錄後（功能展示段） | `d.showcase()`：一個重點功能一頁。左：全頁截圖＋圖解編號；右：同編號說明 ≤ 5；導言一句「這能幫你做什麼」。整段 ≤ 12 頁（建議 5～10） |
| **測試報告**（選了才有） | 功能展示之後、操作說明之前 | `d.acceptance()`：上方 ≤ 4 張指標卡（大數字＋名稱＋一句定義）；下方表「指標｜定義｜結果｜樣本｜測試日期」≤ 8 列；底部一句測試範圍。最多 2 頁 |
| **整合測試**（選了才有） | 測試報告之後、操作說明之前 | `d.itest()` 一次產生：測試範圍與結果、問題一覽、每個問題一頁（截圖標框＋步驟／預期／實際／建議）、通過項目（文字逐條）、未測項目 |
| 分隔頁 | 每部分開頭 | PART 標籤、標題、一句話、本部分頁目（省略 `items` 自動列＋頁碼）；同時是目錄的分組 |
| **全景圖解** | 大功能的主畫面 | 全頁截圖＋藍色編號框；右側同編號說明（5～7 個） |
| **流程** | 一個完整操作 | 左：編號步驟（4～7 步）；右：1～2 張局部截圖 |
| 狀態機 | 有模式／狀態切換 | 三個方塊＋箭頭＋觸發條件；下方「怎麼回來」；注意框 |
| 讀懂 | 系統給的資訊面板 | 局部截圖＋三欄表「區塊｜怎麼讀｜發現問題時」 |
| 指令 | 要在終端打指令的步驟（安裝、登入、更新） | 左：`d.term()` 終端框（指令＋實際輸出，密鑰遮蔽）；右：步驟＋「看到什麼代表成功」 |
| 桌面視窗 | 步驟發生在 app 網頁以外（LINE 桌面版、第三方工具） | `desktop_shot.py` 拍的截圖（自動包視窗框）＋編號說明或步驟；規則同全景／流程頁 |
| **控制點地圖** | 參數章節開頭 | 六格流程，每格列出控制它的設定 |
| **參數頁** | 每組相關設定 | 左：欄位局部截圖；右：「設定（目前值）｜情境 → 結果」表 |
| 速查表 | 參數章節結尾 | 「看到的狀況｜先檢查｜要改的地方」 |
| 維護節奏 | 最後幾頁 | 四欄：每天／每週／活動上下檔／改版 |
| 附錄 | 倒數第二頁 | 目前設定值一覽（從線上讀） |
| 封底 | 最後一頁 | `d.back_cover()`：一句話、摘要、聯絡列（自動帶公司名與 ai-go.app） |

## 功能展示

Phase 0 選了「功能展示」才做。讀者是決策者或 demo 的觀眾：**看完知道這支 app 能幫他做什麼**，不是學會操作。

- **一個重點功能一頁**，挑 5～10 個，核心工作流程優先；其他頁面、設定細節留給操作說明
- **頁標題＝功能名**（畫面上的叫法，短）；**導言＝一句「這能幫你做什麼」**（≤ 40 字），寫它做什麼、會怎樣：
  好「客人問訂單，系統直接查好回覆，不用切到後台」；壞「智慧客服，大幅提升效率」
- **截圖用全頁**，圖解編號 ≤ 5，說明寫「這塊讓你看到／做到什麼」，不寫「按這裡 → 再按那裡」
- 不寫形容詞與推銷語（強大、智慧、無縫、大幅提升）、不和其他系統比較、不寫怎麼做出來的
- `value` 也要能查證（G3）：寫的是它現在真的做得到的事，不寫規劃中的功能

## 測試報告

Phase 0 選了「測試報告」才做（`workflow.md` P1／P2）。只整理開發過程**已有**的測試數據，不另外跑測試。

- **數字照來源抄**：含分子分母（「98.2%（491／500）」），不重算、不四捨五入成更好看的值、不挑對自己有利的那一次
- **每個指標一句白話定義**，讓讀者知道「對」是怎麼算的：好「總金額與人工核對完全相同的比例」；壞「Accuracy」
- **樣本與範圍要寫**：幾張、從哪來、哪些情況不在測試範圍（例：手寫收據）
- **不寫**：調參過程、模型名稱、和舊版或其他系統比較、「準確度極高」這類評價
- `sources` 必填：評估紀錄或測試報告的路徑，不印進手冊，G3 查證與 P7 交付回報用

## 整合測試

Phase 0 選了「整合測試」才做（`integration-test.md`）。讀者是專案負責人或驗收的人：**看完知道哪些能用、哪些要修、修多急**。

- **判讀（`judgement`）一句白話**（≤ 90 字）：看到什麼 → 為什麼不合理 → 影響誰。
  好「建立訂單後列表沒有更新，使用者會以為沒建成功而重複建立」；壞「列表 state 沒 refetch」「有 bug」
- **嚴重度照影響判**：高＝核心流程走不下去或資料錯；中＝能用但結果或訊息不合理；低＝文案、版面。不因為好修就降級
- **通過的「結果」寫看到什麼**（`c.note()`）：好「列表最上面出現 IT-001，金額 1,200，後端一致」；壞「OK」「正常」
- **不寫**：程式碼位置、怎麼修的細節（`suggest` 一句就好）、責怪誰；不把疑慮寫成未通過來顯得嚴謹，也不把未通過寫成疑慮來顯得好看
- **未測的一定列出原因**：讀者要知道哪些沒驗過、要另外怎麼驗
- 修好重測通過的，`fixed` 寫一句「原本…，已修正」；不刪掉這筆紀錄

## 「情境 → 結果」的寫法（參數頁的核心）

每一列回答三件事：**改成什麼 → 使用者遇到什麼情況時 → 會發生什麼（以及副作用）**。

好的例子：
- 「閒置幾小時算新話題　6」：客人早上問商品尺寸、晚上再來問訂單 → 當成新話題，銷售進度重來，客人卡仍在。調短（2）→ 同一天下午回來也不延續上午的推薦；調長（24）→ 隔天回來還接著聊，但舊話題可能干擾新問題。
- 「轉真人關鍵字」：客人訊息含這些字 → 立即待人工，只回轉接語，不經 AI。**別加太泛的字**（例：「客服」），一般詢問也會被轉走。

不好的例子：
- 「閒置時數：設定閒置多久算新 session。」（只是把欄位名換句話說）
- 「調整此值可優化體驗。」（沒有情境、沒有結果）

規則：
- 第一欄寫**設定名＋目前值**（從線上讀）
- 講清楚是**硬限制還是對 AI 的要求**（例：字數上限是寫進提示詞，不是硬截斷）
- 有範圍就寫範圍；有建議值就寫建議值與理由
- 關掉／清空會怎樣一定要寫（很多人會誤關）
- 會影響客人、無法收回的，用注意框

## 說法查證（G3）

每一句「系統會怎樣」都要能指到下面其中一個：

1. 程式碼（前端 hint、後端實際判斷）—— 以後端為準，前端說明可能過時
2. 線上設定值
3. 本次實測（截圖、測試對話、送出的測試訊息）

查不到 → 刪掉或改寫成可查證的版本。常見要查的：
- 開關關掉後的實際效果（兩個開關可能其實效果相同）
- 時段能不能跨夜
- 「完成」之後客人再來訊會怎樣
- 等待訊息的頻率是「每 N 分鐘最多一次」還是「每則都回」
- 內部筆記 AI 會不會讀
- 旅程／群發在人工處理中會不會暫停

## 圖解編號

- 同一張圖 3～7 個編號；超過就拆頁
- 編號順序＝說明順序＝視線順序（通常左→右、上→下）
- 說明寫「是什麼＋做什麼」，不要只寫名稱

## 注意框的用法

只放三種內容：**不可逆**（對外發送、刪除）、**常見漏接**（忘了交回、忘了刪待補主題）、**容易誤設**（太泛的關鍵字）。一頁最多兩個。
