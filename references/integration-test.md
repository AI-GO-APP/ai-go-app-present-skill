# 整合測試（第五種用途）

Phase 0 選了「整合測試」才做。目的：交付前把 app **每一頁、每個可點的 UI、每條端到端流程都實際點跑一次**，
除了「有沒有壞」，還要判斷**畫面與訊息合不合理**——該有反應的有沒有反應、錯誤訊息看不看得懂、
數字和狀態對不對得起來。產出一份 PDF：**通過的逐條文字描述、免截圖；未通過或有疑慮的逐項截圖＋說明**。

和「測試報告」不同：測試報告只整理開發過程**已有**的數據、不另外跑；整合測試是**這次實際去跑**。

## 架構總覽

```
IT0 範圍與安全 → IT1 盤點 → IT2 測試計畫 ══GT1 使用者核准══ → IT3 準備資料 → IT4 執行（itest.mjs）
→ IT5 判讀 ══GT2 每個問題看過截圖══ → IT6 報告（d.itest()）══G4 逐頁目視══ → IT7 交付、問要不要修
```

| 層 | 誰做 | 工具 |
|---|---|---|
| 測試案例（要測什麼、預期什麼） | 你：讀程式碼與規格寫 `itest.plan.mjs` | 範本 `templates/itest.plan.example.mjs` |
| 執行與自動偵測 | 腳本 | `scripts/itest.mjs`（規則在 `itest_core.mjs`） |
| 合理性判讀 | 你：看截圖、對照後端 | `review.json`（GT2） |
| 報告 | 腳本 | `Deck.itest()` → 同一套 PDF 母版 |

### 四個測試層

| 層（群組） | 測什麼 | 怎麼寫 | 會不會改資料 |
|---|---|---|---|
| **冒煙 smoke** | 每一頁打得開：有內容、沒有程式錯誤、API 都成功 | `t.smoke()`（預設 `present.config.json` 的 `routes`） | 不會 |
| **UI 巡檢 sweep** | 一頁上**每個**按鈕、分頁、連結都點一次：有沒有反應、點了有沒有出錯 | `t.sweep({ route, name, prepare })`，一個畫面狀態一個（例：設定頁的每個分頁各一個） | 不會：會改資料的字一律略過 |
| **端到端 e2e** | 核心流程從頭到尾：建立 → 列表看到 → 修改 → 查詢 → 刪除；結果對回後端 | `t.case({...}, async (c) => {...})` 一條流程一個案例 | 會：只用測試資料 |
| **表單驗證 form** | 必填空白、格式錯、邊界值、超長、特殊字元 → 擋得住、訊息看得懂 | `t.case`，用 `c.expectText("請輸入名稱")` 斷言預期的錯誤訊息 | 通常不會（被擋下） |

可以再加 **權限 role**（不同角色看到／做得到的不同）等群組；群組名自己取，`export const labels` 給報告上的名字。
沒測的（會真的扣款、推播給真客人、第三方後台）用 `t.skip({ reason })` 列出來，報告最後一頁寫原因——**不能悄悄漏掉**。

### 自動偵測（每個案例、每次點擊都做）

| 偵測 | 判定 | 說明 |
|---|---|---|
| 未攔截的 JS 例外 | 未通過 | `pageerror` |
| API 回 5xx | 未通過 | 4xx 記疑慮（權限、驗證）；預期中的 4xx 用 `allowStatus: [422]` 放行 |
| 畫面露出堆疊、錯誤名稱、伺服器錯誤原文、`[object Object]` | 未通過 | 使用者看到就是錯 |
| 畫面出現 `undefined`／`NaN`／`null`／`Invalid Date`、JSON 錯誤原文、沒代換的 `{{變數}}` | 疑慮 | 多半是資料沒接好，看截圖確認 |
| 錯誤提示框（toast、alert、`.error`）出現「失敗／錯誤／無法…」 | 疑慮 | 案例自己預期的錯誤訊息用 `c.expectText()`／`allow` 放行 |
| console 錯誤、連線失敗 | 疑慮 | `itest.ignore_console`／`ignore_urls` 排除已知雜訊 |
| 畫面空白 | 未通過 | 沒有任何文字或圖片 |
| 卡在「載入中」超過 8 秒 | 疑慮 | `itest.loading_wait_ms` 可調 |
| 出現橫向捲軸 | 疑慮 | 版面超出視窗 |
| **點了沒有任何反應**（巡檢） | 疑慮 | 畫面、網址都沒變，也沒送請求。導覽列連到目前這頁不算 |
| 瀏覽器原生對話框（confirm／alert） | 只記錄 | 預設按「取消」；要按確定用 `c.acceptDialogs()` |

**重現**：未通過的案例自動再跑一次（`mutates: true` 的不重跑，避免重複建資料）；巡檢有問題的點擊重載後再點一次。
第二次正常 → 改記疑慮「偶發」；第二次一樣 → 記「重現 2 次」。這就是 P4 確認清單的「重現兩次以上」。

**證據**：每個案例結束都截一張全頁 `shots/it-<編號>.png`，問題元素（出錯的字、點的按鈕、斷言對象）自動編號標框。
報告只放未通過／疑慮的截圖；通過的截圖留著給 GT2 看總表。

### 合理性判讀（自動偵測抓不到的，要你看）

腳本只抓得到「明顯的錯」。**UI 預期合不合理**要你看截圖、對照程式碼與後端判斷（GT2 清單）：

- [ ] **回饋**：按了有沒有讓人知道成功或失敗（儲存後沒有任何提示、按鈕沒變 loading 可重複按）
- [ ] **訊息看得懂**：錯誤訊息是給使用者看的話，不是技術原文；說了要怎麼辦
- [ ] **前後一致**：成功提示和實際結果一致（說「已建立」但列表沒有）；計數和列表筆數一致；同一個東西各頁叫法一樣
- [ ] **資料正確**：金額、日期、時區、單位、排序對；對回後端（`c.api()` 或讀設定 API）
- [ ] **狀態合理**：空狀態有說明（不是一片白）、停用的按鈕看得出停用、權限不足有說明
- [ ] **流程走得通**：從入口到完成不用繞路或重新整理；返回、取消不會遺失資料
- [ ] **版面**：文字沒被切掉、按鈕沒被蓋住、表格沒有破版

## IT0 範圍與安全（先問，`prompts.md` §10）

1. **環境**：測哪個站（demo 租戶／正式租戶／developer 預覽頁）。預設 demo 或預覽頁；正式站要使用者明確同意
2. **測試帳號與角色**：用哪個帳號；要不要測多個角色
3. **可以改哪些資料**：端到端會建立／修改／刪除——只動「測試資料」（名稱前綴 `IT-`、測試客人）；哪些表不能碰
4. **對外送出**：LINE 推播、Email、簡訊、付款、第三方 webhook——預設**不測**（`t.skip`），或只對使用者自己的測試帳號
5. **範圍**：全部頁面？哪幾條是核心流程？有沒有規格或驗收條件可以對（有的話預期就照規格寫）

## IT1 盤點

- `discover.mjs` 拿每頁小圖與 `ui.json`（分頁、按鈕、欄位）——這就是巡檢與冒煙的路由清單
- 讀前端：路由、每頁的操作、表單的驗證規則、錯誤訊息文字
- 讀後端：每個操作呼叫哪個 action／API、會不會改資料、會不會對外送出、回什麼錯
- 大型 app 派 Explore 子代理並行盤點（`prompts.md` §11）
- 列出**有副作用的操作**清單：這些巡檢不會點，要決定寫成端到端案例（測試資料）還是 `t.skip`

## IT2 測試計畫 → GT1

1. 寫 `itest.plan.mjs`（範本 `templates/itest.plan.example.mjs`）。每個端到端案例都要有：
   - `id`（`E2E-01`、`FRM-03`…，報告上的編號）、`area`（畫面上的頁名）、`title`（短，進目錄）
   - `expect`：預期結果，**有依據**（規格、程式碼、線上設定）；`basis` 記依據（不印進報告，判讀用）
   - `mutates: true`：會改資料的流程（不自動重跑）
2. `node <skill>/scripts/itest.mjs --config present.config.json --list` 不開瀏覽器列出全部案例（markdown 表）
3. 用 `templates/itest.outline.example.md` 的格式提給使用者：測試層、案例數、核心流程清單、不測的項目與原因、
   會改哪些資料、要確認的點（最多 3 個）。**核准才開跑**

## IT3 準備資料

- 測試資料用固定前綴（`IT-20261007-…`），跑完好清；需要的示範資料先用 app 自己的 action 預填
- 會被改到的狀態先備份：`python <skill>/scripts/prep_state.py backup --table … --fields …`
- 巡檢會點開分頁、對話框、選單，**也可能點開對話把未讀歸零**——一樣先備份

## IT4 執行

```bash
node <skill>/scripts/itest.mjs --config present.config.json                 # 全部群組
node <skill>/scripts/itest.mjs --config present.config.json e2e form        # 只重跑某幾組（其他組結果保留）
```

- 輸出 `itest/results.json`（全部案例與發現）、`itest/review.json`（判讀檔；未通過／疑慮自動補空白骨架）
- 每一行 `PASS／FAIL／DOUBT／SKIP 編號 標題`，問題的前三個發現接在下面
- 群組中途丟例外不會拖垮整批：記一筆 `GRP-<群組>` 未通過，接著跑下一組
- **跑的過程不修 bug**：整份跑完才判讀。報告要反映「測的當下」的狀態；修是 IT7 的事
- 跑完立刻還原資料（`prep_state.py restore`／`diff`），清掉 `IT-` 前綴的測試資料

### `present.config.json` 的 `itest` 區塊（都可省略）

| 鍵 | 預設 | 用途 |
|---|---|---|
| `account` | — | 報告上寫的測試帳號（例：「測試帳號（管理員）」），不要寫密碼 |
| `settle_ms` | 1200 | 每個動作後等畫面穩定 |
| `route_wait_ms` | 2500 | 換頁後等多久 |
| `loading_wait_ms` | 8000 | 「載入中」超過多久算疑慮 |
| `sweep_max` | 60 | 巡檢一個畫面最多點幾個（超過的列為略過） |
| `sweep_skip` | — | 巡檢額外不點的字（例：「同意」） |
| `ignore_urls`／`ignore_console` | — | 已知雜訊（第三方追蹤、字型） |
| `allow_text` | — | 全域放行的畫面字（例：資料本身就含 `null` 字樣的欄位） |

### 案例 API（`c`）

| 方法 | 做什麼 |
|---|---|
| `c.go(route)`、`c.click(spec)`、`c.mouseClick(spec)`、`c.type(spec, text)` | 操作，自動記成報告上的步驟 |
| `c.step("等 AI 回覆")` | 手動補一句步驟 |
| `c.expectVisible(spec)`／`expectGone(spec)` | 元素出現／消失（預設等 6 秒） |
| `c.expectText(text)`／`expectNoText(text)` | 畫面有／沒有這段字；`expectText` 同時放行這段字（預期的錯誤訊息） |
| `c.expectUrl(part)`、`c.expect(cond, msg, spec?)`、`c.fail(msg, spec?)` | 其他斷言；給 spec 會在截圖上標框 |
| `c.doubt(msg, spec?)` | 能用但不合理 → 記疑慮，繼續跑 |
| `c.note(text)` | 通過時的觀察，報告「結果」欄就寫這句（例：「列表最下面出現 IT-001」） |
| `c.allow(422, "請輸入名稱")` | 放行預期中的 HTTP 狀態或畫面字 |
| `c.api(path, { method, body })` | 用同一個登入身分打平台 API，核對後端資料 |
| `c.acceptDialogs()` | 原生 confirm 按確定（預設取消） |
| `c.get`、`c.run`、`c.p`、`c.T`、`c.F`… | 同 `lib.mjs` session |

## IT5 判讀 → GT2

1. 拼總表看**全部**截圖（通過的也看）：`python <skill>/scripts/contact_sheet.py "shots/it-*.png" --out disc/it-sheet`
2. 每個未通過／疑慮案例開單張大圖，照上面的合理性清單判斷，寫進 `itest/review.json`：

```json
{
  "E2E-03": {
    "run": "（腳本填好，不要改）",
    "status": "fail",
    "severity": "高",
    "judgement": "建立訂單後列表沒有更新，使用者會以為沒建成功而重複建立。",
    "actual": "按「建立」後出現「已建立」，但列表要重新整理才看得到",
    "suggest": "建立成功後重新讀取列表"
  }
}
```

| 欄位 | 規則 |
|---|---|
| `status` | 可改判：誤判 → `pass`（judgement 寫理由，進通過清單）；自動通過但看了覺得不合理 → `doubt`（要先在 results 找到該案例的 `at` 填進 `run`） |
| `judgement` | **必填**，一句白話（≤ 90 字）：看到什麼、為什麼不合理、影響誰。這句是問題頁的導言與問題一覽的內容 |
| `severity` | 未通過必填，疑慮選填：**高**＝核心流程走不下去或資料錯；**中**＝能用但結果或訊息不合理；**低**＝文案、版面 |
| `actual`／`suggest` | 選填：實際狀況補充、建議修法（一句） |
| `observed` | 通過案例選填：覆寫報告「結果」欄 |
| `fixed` | 修好重測通過後填（見 IT7） |

- 判讀前照 `workflow.md` P4 的**確認清單**排除假問題：不是資料問題、不是權限、不是平台規則（簽核 `pending`、冷啟動 503）、
  不是測試方式造成（程式點擊、內層捲動、viewport）。假問題改判 `pass` 並寫理由，或修計畫重跑
- 重跑過的案例 `run` 會對不上 → 判讀過期，要重看（`d.itest()` 會擋）

## IT6 報告

```python
d = Deck.from_meta("disc/meta.json", purposes=["整合測試"], shots="shots", version="VFS v12")
d.cover("後台每一頁、每個按鈕與核心流程實際操作一次的結果", meta=[("對象", "專案負責人")], hero="it-SMK-home")
d.itest(scope="範圍：後台 6 頁＋4 條核心流程；LINE 推播不在範圍內")   # 讀 itest/results.json＋itest/review.json
d.back_cover("有問題時", "未通過的項目修正後會重測並更新這份報告。")
d.write()
```

頁面（全部自動產生、自動進目錄）：

| 頁 | 內容 |
|---|---|
| 測試範圍與結果 | 四張數字卡（通過／未通過／疑慮／略過）、各測試層統計表、範圍與環境（網址、帳號、瀏覽器、時間） |
| 問題一覽 | 未通過在前、疑慮在後：編號｜區域｜判讀｜判定｜嚴重度（每頁 10 列） |
| 每個問題一頁 | 左：全頁截圖（問題處編號標框）；右：判定與嚴重度、步驟、預期、實際（編號對應截圖）、建議 |
| 通過項目 | 文字逐條、免截圖：編號｜區域｜測了什麼｜結果（每頁 12 列，`per_page` 可調） |
| 未測項目與原因 | `t.skip` 的項目 |

`write()` 會印出問題清單（P7 交付時列在對話裡）。之後照 `workflow.md` P6／G4 渲染與逐頁目視。

## IT7 交付、問要不要修

- 交付 PDF，對話裡列出未通過／疑慮清單（`write()` 印的那段）
- **問使用者要不要現在修**（整合測試的目的是找問題；修是另一件事，範圍可能很大）。要修就用 aigo-builder 照該 app 的發布規則修，
  修完重跑受影響的群組 → 那幾個案例變通過 → `review.json` 裡 `fixed` 填一句「原本…，已修正」→ 重出報告，
  通過清單會標「修正後重測通過」
- 還原資料、清測試資料；`itest/`、`shots/` 留在工作資料夾，下次改版直接重跑

## 安全規則

- **巡檢只點不會改資料的元素**：`DANGER` 字（刪除、儲存、送出、確定、匯出、登出、付款…）、`type=submit`、
  開新視窗／下載／外部連結、勾選框與開關一律不點；這些由端到端案例在測試資料上測
- 巡檢遇到原生 confirm 一律按「取消」
- 端到端只動測試資料；會對外送出的只對使用者自己的測試帳號，否則 `t.skip`
- 截圖一樣過密鑰檢查（G2 清單第一條）
- 不在正式站跑會改資料的群組，除非使用者明確同意
